01 · 概述与定位

unit-test-selfcheck 把单测规范工程化为「固定入口 + 机械脚本 + 归档前质量闸门」，源于实战教训：规范靠自觉被证明不可靠，于是自觉被替换成了证据。

AI 产出语义·机器保证确定性·验收结论须可复核

02 · 设计思路

设计决策的底层逻辑——每张卡是一条独立的思考线索。

①设计出发点源于实战教训
JSZ-960 项目证明「规范靠 AI 自觉」不可靠。因此十阶段规范被工程化为强制序列与归档闸门——测试必须真实执行（surefire 原文存档…
②思路 2
自检报告的定位是「证据的归档」而非「结论的陈述」：报告里每个结论都能被证据附件复核，闸门逐条比对汇总与明细、报告与原文的一致性。

输入 → 机制 → 验收 → 产出：验收层独立判卷，生成与验收物理分离。

06 · 解决的痛点

每一格都是真实踩过的坑——工具设计由此反推。

漏输出报告、验证 SQL 未真实执行缺陷编号悬空引用、汇总与明细矛盾规范靠 AI 自觉，流程跳步AI 味文本混入正式报告

07 · 机制深拆

6 项核心机制，每张卡：一句话核心 → 机器化要点 → 业务价值。逐项展开见各卡细节。

01双模式设计
模式 1 研发自检：完整 12 步强制序列，产出 5 份归档报告。
◆ 一个工具同时服务「自检归档」与「测试左移」◆ 模式 2 是与 E2E 的桥梁：探测结果双源补用例◆ schema 同款是契约化联动的样板
02git 分析定必测
自检范围不靠人挑：分析 git 提交历史，结合变更文件与依赖关系，机械生成必执行测试类清单。
◆ 变更驱动测试范围，漏测在源头被堵◆ 清单机器生成，可复算◆ 与范围表达式共享「机械圈定」哲学
03真实执行与原文存档
测试必须真实执行，执行原始输出全量存档备查。
◆ 执行原文存档是复检的物理基础◆ 结论对不上原文即 FAIL◆ 存档随报告归档，长期可查
💼 这条机制直接源于实战教训：曾经「规范靠自觉」被证明不可靠。现在，自觉被替换成了证据。
04验证 SQL 先执行后落笔（F4）
每条验证 SQL 的状态机：未执行（NOT-EXECUTED）不许写结论；
◆ 先执行后落笔是硬性时序◆ NOT-EXECUTED 项显式暴露，转人工补执行◆ 数据库访问走共享只读通道
05缺陷编号一次生成不改号（F6）
BUG-YYYYMMDD-NNN 编号全局唯一、一次生成、永不改号。
◆ 编号是追溯链的铆钉◆ bug_refs 闸门防空悬引用◆ 编号规范全体系通用
06十项归档闸门
归档前 10 项机器闸门：文件齐套、目录命名、证据引用真实、缺陷编号不悬空、汇总明细一致、报告对执行原文一致、API 章节完整、必需章节齐套、去 AI 化、修复时间记录。
◆ 汇总与明细一致性是实战教训的直接转化◆ 去 AI 化禁词扫描保证报告语言像人写的◆ 10 项全过才允许归档，凭证留存

19 · FAQ

点击展开——最常见疑问的直答。

Q怎么证明测试真的跑过？
真实执行 + 原文存档 + 一致性闸门比对
Q验证 SQL 没执行能写结论吗？
不能，先执行后落笔，状态强制标记
Q缺陷编号会重复吗？
全局唯一、一次生成不改号，闸门防空悬
Q能只探测不写报告吗？
可以，模式 2 即轻量探测
Q10 项闸门会不会太严格？
每一项都对应一个真实踩过的坑。闸门的严格程度 = 历史的疼痛程度。
Q模式 2 探测准确吗？
探测基于 git 事实，准确性有物理保障；它是 E2E 的输入之一而非唯一来源。
Q非 Maven 工程能用吗？
当前绑定 Maven 工程结构，非标准结构需在 config 中适配——这是已声明的边界。
