Executive Brief · 业务向速览

业务速览：价值 · 场景 · 边界

不看代码也能读懂的一页：它解决什么、怎么解决、带来什么。括号内为对应机制名，技术细节见后续章节。

🐢
它解决什么

版本回归靠人点：一轮全量以天计，挤占版本窗口；「全绿」报告无法复核，出了问题难追溯；定位与业务经验散在个人脑中，人员一换测试能力清零。

⚙️
它怎么解决

五源输入（需求/规格/代码/数据口径/知识库）一次声明，机器自动产出用例并执行；界面断言之外强制数据实证（双轨断言），最终产出带防伪核验的归档报告；AI 只做工序内的语义判断，产出必经机器验收（验收戳）。

📈
它带来什么

时间：机械阶段无人值守、夜间自动执行，不占版本窗口；可信度：报告每个数字可被第三方离线复核（attest.py），篡改/虚报检出率 14/14；可交接性：规则与经验沉淀为配置与知识库，换需求开箱即用（init_project）。

需求材料（五源输入）机器解析 · 生成用例环境预检（不达标即停）
自动执行（读/写链路）数据实证核验失败归因 + 21 项质量闸门 ⛨
核验报告（可归档）第三方离线复核 ✓（attest.py）

不熟悉术语？可先查附录术语表，或切换到右上角「👔 业务视角」只看业务解读。

🔄 版本迭代回归

每次发版前的全量 UI 回归由机器无人值守执行（机械阶段）：从「人点三天」变为「夜间一次执行窗口」，结果可复跑、可对比。

能力锚点 → 八阶段流水线 · 缓存与断点续跑
✅ 需求验收

新需求上线前，从需求材料直接生成用例并产出验收证据：界面表现与后台数据双重核验（双轨断言），杜绝「页面显示成功、实际没落库」的假通过。

能力锚点 → init_project 五源输入 · verify_data 数据实证
🤝 跨人交接

测试经验沉淀为知识库与规则配置而非个人记忆，人员变动后能力不缩水；业务规则集中在一处维护（单一规则来源 contract.json），口径不随人走。

能力锚点 → 三层知识库 · contract.json
📦 外包/供应商交付验收

交付物附带可独立复核的证据链：第三方无需信任交付方，用独立小工具（attest.py，221 行单文件）离线重算即可验证报告真伪。

能力锚点 → 链式 hash · attest.py 离线复核
🧾 审计与留痕

每轮执行的用例、证据、数字全部留档并串成防篡改链，任何事后改动（改数、删文件、换报告）都会在复核时断裂定位，满足审计可追溯要求。

能力锚点 → run_dir SSOT · manifest 链式 hash
🧯 质量红线守门

21 项确定性质量闸门在出报告前强制检查：引用不存在、数字对不上、证据过期等任一命中即整体 FAIL 且禁止归档，「带病的绿」发不出去。

能力锚点 → 闸门体系 G-01~G-21
它不是什么：① 不替代真机/兼容性测试——执行层是浏览器自动化（Playwright），不覆盖 App 真机矩阵；② 不做性能压测——有步骤级耗时遥测，但不产出并发压力指标；③ 不做安全渗透测试——「攻击防御」指对报告本身的防篡改，而非对被测系统的渗透；④ 不承诺业务语义无人复核——机械阶段支持无人值守，AI 语义判断的业务类结论按设计强制人工复核（pending_review）。
PART 01 · 设计思想 DESIGN
01
Framework Design · 设计总纲

框架设计：从一次「假绿」事故说起

本章是设计总纲：先讲设计思路（三条公理），再讲设计过程（四步推导），然后给出框架全景（五层架构与决策），最后摊开设计取舍。先业务语言，括号内为技术锚点，细节在后续章节展开。

💼
业务解读：这一章回答「它为什么长成这样」。结论先行：所有设计都不是炫技，而是从一次真实事故反推出来的——每一个机制都能追溯到一类具体的「被骗方式」。

2025-09-29 PROJ-179「假绿」事故：报告全绿、数字却无法从执行记录复核——问题不在人，而在流程把可信寄托在人的自觉上。由此立下三条不可让渡的设计公理：

①机械环节全脚本化

凡是能用确定性代码做的，绝不交给概率性判断。解析、生成、执行、核验、报告全部由脚本完成，人（和 AI）不手工搬运中间结果。

→ 八阶段流水线唯一入口 atw.py · 33 个可执行脚本
②AI 产物必经机器验收

AI 只做语义加工（断言设计、归因、覆盖判定），产出必须过确定性验收器打戳（gated_at），无戳的产物下游一律拒绝消费。

→ 三段式：备料 brief → AI draft → 脚本验收打戳 · ai_gate.py 57 行
③一切结论可证伪

报告里的每个数字都能从盘上产物重算（claims 对账），每个引用都能被独立工具复核——复核者不依赖执行环境、不需要信任交付方。

→ manifest 链式 hash · attest.py 离线复核器（221 行单文件）

设计方法固定四步：问题清单 → 威胁建模 → 机制设计 → 闸门固化——明确防什么（四类威胁）、也明确不防什么；全部规则收敛到 contract.json 单一来源，编译分发为 lint / precheck / gate 三通道共 21 项闸门。

展开：五层职责 × 设计决策明细表

🖥️ 单机单会话

同一需求同一时刻只允许一个 run，不做分布式并发调度。

放弃：横向扩缩容　换来：零部署依赖，每个结果可归因到唯一一次执行

👁️ AI 视觉定位默认关闭

视觉兜底定位（LC-06）默认关闭：AI 只给建议不给坐标、写链路禁用、同元素二次直接 FAIL 人审。

放弃：定位失败时的全自动兜底　换来：成本与风险闸门优先，AI 永远不直接操控页面
🧊 缓存只跳计算不跳验证

内容摘要缓存命中只跳过重复计算，验证类环节每次照跑。

放弃：二次执行的极致提速　换来：可信优先于速度——缓存再热，闸门一道不少
02
Core Design · Controlled RAG & Machine Acceptance

核心设计思想：受控 RAG 与机器验收闭环

本章回答一个问题：AI 在这个框架里到底被允许做什么、被禁止做什么。答案是三条相互咬合的设计思想——受控 RAG、机器验收闭环、经验回流飞轮，共同构成「AI 有能力、机器有否决权」的工程结构。

💼
一句话总纲：让 AI 在机器划定的轨道上发挥语义能力——检索增强（RAG）保证 AI「有依据」，机器验收保证 AI「不越界」，经验回流保证系统「越用越强」。AI 的价值被完整保留，AI 的风险被机器拦截。

AI 不凭空写断言，一切产出从知识库检索开始，走固定四步管道：

①检索 Retrieve

5 个知识库（坑点 / 交互策略链 / 失败指纹 / 环境排障 / 业务规则）三层合并、就近优先；dormant 条目不注入，置信度按月衰减保鲜。

lib/atw_common.py load_knowledge() · 过滤 L138-141 · 初始置信度 L63
②增强 Augment

为每条边界规则生成 brief 备料池（字段 + 数据样本 + 判定指引）——AI 只能基于备料池作答。

bin/gen_cases.py --emit-assert-briefs · bin/coverage_semantic.py
③生成 → ④验证

AI 只写 draft；验收器第④道「引用存在性」要求断言词级命中备料池，不命中即拒——工程化防幻觉。

bin/apply_assertions.py check_draft L106-155

三段式铁律：备料（机器）→ 加工（AI）→ 验收打戳（机器）。五道确定性检查（schema / 一一对应 / 双轨配对 / 时间窗口 / 引用词级命中）；批失败率 >30% 停工人审；无戳产物下游一律不消费。

展开：三段式机器控制点明细表
环节执行者产物机器控制点
备料 brief机器（gen_cases.py）assert_briefs/<brief_id>.json备料池即验收基准：rule.fields + data_samples 键值
语义加工AIcases/assert_drafts/*.json只许加工，不许入库；AI 不触碰任何最终产物
验收打戳机器（apply_assertions.py + ai_gate.py）gated_at + draft_hash 戳五道检查 + 批失败率 30% 停工 + 无戳不消费

每轮执行后 learn.py 沉淀坑点，经人工确认闸（KB-02）才入库；置信度衰减保鲜。LC-06 定位成功后 suggested_locator 自动回流策略链——越用越快、越用越准。

维度裸用 AI传统 RAGE2E-ATW 受控 RAG

产出验证无——写完即用无——依据错了照单全收五道确定性检查，词级回溯备料池

03
Case Review · PROJ-179

案例复盘：PROJ-179 假绿拦截链

2025-09-29 PROJ-179「假绿」事故回放，以及同一剧本今天会被哪几道闸门拦下。

① 执行
PROJ-179 库存调拨需求进入 UI 自动化回归，用例在目标环境执行
② 出报告
汇总产出测试报告——但报告与真实执行产物之间没有绑定关系，数字靠人工转填
③ 报告全绿
报告结论「全部通过」，按流程归档，版本据此放行
④ 人工抽查
抽查发现报告数字与实际执行记录对不上：证据引用无法核实，数字无从回溯重算
⑤ 定位「假绿」
结论定性：报告是「假绿」——绿的只是文档，不是执行。问题根源是流程把可信寄托在人的自觉上

同一份「假绿报告」走今天的流程，会被四道关卡依次拦截：G-13 拦陈旧数据 · G-14 拦幻觉引用 · G-15 拦虚报数字 · 链式 hash 拦事后替换；归档后 attest.py 仍可离线独立重算复核。

技术锚点：G-13 check_freshness（freshness_hours 2h + unexpected==0）· G-14 report_refs 存在+非空+sha256 · G-15 源产物 sha256 重算 + report_extract 报告数字提取 · attestation.json 链式 hash · attest.py 离线复核

实证项结果
PROJ-179 资产减值全量回归54 用例全绿收口 产出 V4 完整版报告（操作内容 + 截图实录）
全量执行基线63 tests 全量执行基线建立（机器执行跑通）
攻防复核（attack_recheck）14/14 五类攻击样本全部检出
💼
业务解读：同一个 PROJ-179，当年靠「信人」出了假绿，今天靠「信机器」做到 54 用例全绿且每个数字可被第三方复核——差别不在人更仔细，而在流程不再给「假绿」留位置。
PART 02 · 架构与实现 ARCHITECTURE
04
Architecture

总体架构设计

三层分工与端到端数据流。硬性环境约束：Python 3.6 兼容 · Python 层零额外三方包 · 单机单会话 · DB 通道只读 · 知识库 00~03 章只读 · 配置脱敏。

💼
业务解读：分工逻辑一句话——重复劳动全交给机器，AI 只做判断且必须过机器验收，质量红线由机器把关。Python 层零额外三方包、单机可跑，意味着引入成本低、不增加运维与供应链风险。

AI 只做判断与加工：断言设计、失败归因、覆盖判定、定位建议。

AI-01 / AI-02 / AI-03 三段式 → 确定性验收器 + gated_at 戳
🚧
闸门层

21 项确定性检查，任一非零退出即终止流水线并禁止归档。

链式 hash 算法

chain_hash = sha256(prev_chain + artifact.sha256 + stage)

manifest.json = { artifacts: [{ path, sha256, producer, stage, chain_hash }] }（有序登记）
add_artifact：同 path 同 sha256 跳过（幂等）；同 path 不同 sha256 原位替换并重算后继链
复核判定逻辑
① 文件完整性每条 artifact 重算文件 sha256 与登记一致；缺失即 FAIL 并定位条目号
② 链完整性逐条重算 chain_hash；增删换序 / 前置被改即「chain_hash 断裂」定位条目
③ claims 对账每条 claim 从源产物重算期望值比对（源产物被替换/陈旧检出）+ 报告文本正则提取数字对比（虚报检出）

AI 产物本质是外部写入的文件，天然不可信。统一「脚本备料 → AI 加工 draft → 脚本验收入库」三段式，gated_at 戳防篡改与漂移。

💼
业务解读：对「AI 写的结论能不能信」的正式回答：不能盲信，所以所有 AI 产出必须过机器验收盖戳，没戳的内容下游一律拒收。AI 是助手，不是签发人。
备料脚本 --emit-*-briefscases/<briefs>/（带 schema + 判定指引）
AI 语义加工 → drafts/*.json验收脚本 --apply / --import ⛨write_stamped 打戳 ✓
下游消费方is_gated 校验 ⛨无戳拒绝 ✗
接口（lib/ai_gate.py，57 行）语义
content_hash(obj)去戳后内容稳定序列化的 sha256 前 16 位
stamp(draft, ts)打戳 {gated_at, draft_hash}，幂等
is_gated(draft)gated_at 存在且 hash 等于当前重算值（防戳后篡改）
write_stamped(...)写回带戳 draft（UTF-8，indent=2）

业务用例 / 执行圈（L2 / L3）L2 = 17 字段人工可读业务用例；L3 = 可执行脚本（spec.ts）
