01 · 概述与定位

spec-toolkit 是规格层的验证基座：七个命令覆盖规格书从骨架到验收的全流程。

AI 产出语义·机器保证确定性·验收结论须可复核

02 · 设计思路

设计决策的底层逻辑——每张卡是一条独立的思考线索。

①设计出发点
规格书是开发的合同，合同里每个签名都必须真实。工具把「审计防编造、验收保质量、契约对拍防漂移、三文档联动防分裂」四件事全部机械化，AI 编写的产…
②「拒绝静默」是它的性格
源码根不存在即报错、定位失败即退出。宁可报错停工，不放行任何存疑产物。

03 · 全景工作流

端到端工作流：每个节点要么由脚本机械承载，要么有明确的移交产物。

04 · 架构设计

输入 → 机制 → 验收 → 产出：验收层独立判卷，生成与验收物理分离。

06 · 解决的痛点

每一格都是真实踩过的坑——工具设计由此反推。

AI 编造方法签名与路径，规格书「专业但全错」自查清单跳步漏检，无记录可追责前端/后端/计划三文档口径漂移AI 生成代码的规范无人拦截

07 · 机制深拆

7 项核心机制，每张卡：一句话核心 → 机器化要点 → 业务价值。逐项展开见各卡细节。

01scaffold 骨架生成
前后端规格书模板（BE_TEMPLATE / FE_TEMPLATE）预置全部章节与锚点：后端 9 章 + 2 附录、前端 4 章 + 附录。
◆ 章节锚点固化，缺失即验收 FAIL◆ 双端模板口径对齐（编号体系互相兼容）◆ 已存在拒绝覆盖，防误操作
02source_audit 源码审计
规格书里最危险的是「看起来专业的编造」。
◆ 后端声明对 .java 工程核验，前端对 .vue/.js 核验◆ 源码根不存在即报错——拒绝静默放行◆ 演示中抓出 5 个真实缺陷：编造 API 路径、不存在的异常码引用等
💼 审计防编造把规格书从「AI 的记忆」变成「源码的镜像」——合同里的每个签名都真实存在。
03spec_verify 机器验收（M-xx）
后端 M-01~M-12、前端 M-01~M-10 共 22 项检查点：骨架锚点、编号连续、声明与源码一致、豁免区间正确、附录齐套、版本联动声明。
◆ 豁免区间机制：红线/快照/附录章节合法包含特殊词，不误报◆ section 字段限定编号提取区间，防前缀撞车◆ FAIL 清单精确定位，定向修复
04link 三文档联动（L-01~L-06）
前端规格书、后端规格书、开发计划三份文档的口径漂移是经典事故源。
◆ 版本不一致即拦截◆ 跨文档编号冲突检测◆ 计划任务与规格条目的映射核验
05contract_diff 契约对拍
前端「我以为后端长这样」与后端「实际长这样」的偏差，用对象级相似度匹配在编码前暴露。
◆ 前端 API 封装签名 vs 后端接口定义◆ 对象级相似度，识别改名/缺字段/类型漂移◆ 契约零漂移是规格交付的硬条件
06fe_code_check 前端代码闸门（F-1~F-4）
AI 生成的前端代码入境检查。
◆ 规则源于存量实证，误报率经真实工程校准◆ 被 xx-spec-coding 复用为编码闸门◆ 闸门行为有 smoke 自检
07all 流水线与黄金基线
all 命令串联 scaffold→audit→verify→link→diff 全流程，退出码 0/1/2 直接接 CI。
◆ 一键流水线，CI 直读退出码◆ 工具自身行为可回归◆ 规则变更需同步更新基线，口径演进有迹可循

10 · 设计原则落地

三条全体系公理在本工具的具体落地形态。

◆ 配置即唯一事实源
全部口径集中项目 JSON，改规则不碰代码，工具自身行为可回归。
◆ 拒绝静默
源码根不存在即报错、定位失败即退出——宁可报错不可放行。
◆ 生成与验收分离
scaffold 管产出，verify/link/diff 独立判卷，互不越权。

19 · FAQ

点击展开——最常见疑问的直答。

Q规格书里的方法名怎么保证是真的？
audit 拿声明去源码核验，找不到即 FAIL；源码根不存在直接报错
Q前后端口径不一致能发现吗？
diff 对象级相似度对拍，编码前暴露漂移
Q能接 CI 吗？
all 命令退出码 0/1/2，可直接接入
Q规则调整要改代码吗？
不用，项目 JSON 是唯一事实源
Q审计覆盖不了的声明类型怎么办？
清单外的声明类型默认转人工确认，并可在 config 中扩展新的审计规则——审计覆盖面随项目演进持续扩大。
Q换一个新项目要多少配置工作？
注册一个项目 JSON（源码根、文档路径、编号规则）即可，全部命令即插即用。
Q契约对拍会不会误报？
对象级相似度有阈值控制，且对拍报告区分「确定漂移」与「疑似漂移」，疑似项交人工裁决。
