01 · 概述与定位

xx-spec-writing 是规格三层架构的编写层：写（本技能）→ 验（spec-toolkit）→ 执行（xx-spec-coding）。

AI 产出语义·机器保证确定性·验收结论须可复核

02 · 设计思路

设计决策的底层逻辑——每张卡是一条独立的思考线索。

①设计出发点
写规格书需要业务语义（AI 擅长）与结构确定性（AI 易错）的分离。编写层刻意做薄——只规定「六步强制序列」与「存疑即审计」军规，验收能力全部复…
②思路 2
规格书被当作「下游资产」而非「交付文档」来设计：编码指令集直接驱动 AI 编码，验收标准直接驱动测试用例——规格书的质量决定全链路质量。

03 · 全景工作流

端到端工作流：每个节点要么由脚本机械承载，要么有明确的移交产物。

04 · 架构设计

输入 → 机制 → 验收 → 产出：验收层独立判卷，生成与验收物理分离。

06 · 解决的痛点

每一格都是真实踩过的坑——工具设计由此反推。

撰写既要业务语义又要结构确定性，AI 顾此失彼不确定的技术事实凭记忆写，错误流入下游增量变更顺手改乱其他章节修订无基线，版本混乱

07 · 机制深拆

6 项核心机制，每张卡：一句话核心 → 机器化要点 → 业务价值。逐项展开见各卡细节。

01六步强制序列
初始化 → 审计前置 → 输入装载 → 分章撰写 → 机器验收 → 交付。
◆ spec_init 初始化，已存在拒绝覆盖◆ 审计前置：撰写前先拿事实基准◆ 装载清单明确：需求/DB 设计/知识库/审计快照/成品样例
💼 强制序列把「写好规格书的方法论」从文档变成流水线——方法论的执行力不再依赖个人自觉。
02存疑即审计
撰写中最重要的一条军规：字段名不确定必须回审计，禁止凭记忆写。
◆ 「大概是这样」在规格书中是禁止事项◆ 审计调用留痕，可检查军规执行情况◆ 与 source_audit 的源码核验形成闭环
03范围外不动与存量优先
增量变更两条铁律：只改指定范围（范围外不动，骨架锚点外的变更机器可查）；
◆ 范围外变更机器可查，防「顺手优化」◆ 存量优先保持系统概念的单一来源◆ 修订版本号递增不回滚，基线可查
04验收口径复用 spec-toolkit
编写层不含任何验收逻辑——verify（M-22）、diff（契约对拍）全部命令行直调 spec-toolkit。
◆ 交付口径：双端 M 项全 PASS + diff 零漂移◆ FAIL 修复循环上限 3 轮，仍不过停机汇报◆ 薄编写层是刻意的架构决策
05编号体系
全局唯一且机器可提取的编号体系是跨文档追溯的骨架：后端 API-TR / E-TR / V-xx / SN-xx / F-xx，前端 F-xx / CMP-xx / FS-xx / AC-TR…
◆ 编号即追溯单元，被下游各环节引用◆ spec_config 按区间解析，防前缀撞车◆ 编号冲突在 link 检查中被拦截
06规格书即下游资产
规格书不是写完就归档的文档：后端第 7 章编码指令集（步骤/约束/输入包/红线）直接驱动 xx-spec-coding；
◆ 编码指令集：AI 编码的范围与约束来源◆ 验收标准：手工与自动化双轨用例的共同上游◆ 规格书质量决定全链路质量
💼 「规格书即资产」意味着写规格书不是 paperwork——它直接进入生产线，写错一处，下游处处错。

◆ 薄编写层是刻意的

◆ 规格书是资产不是文档

→

⚠顺手改了别的章节
→
🛡范围外不动：骨架锚点外变更机器可查

🛡存量优先检查，禁止新建可复用定义
⚠验收标准不可测

→

19 · FAQ

点击展开——最常见疑问的直答。

Q增量修改会不会动到别的章节？
范围外不动机器可查：锚点外变更会被发现
Q为什么要编写/验证分离？
职责分离：写的人不判卷，验证标准独立演进
Q规格书写完就结束了吗？
不是，编码指令集与验收标准直接驱动下游
Q业务口径哪里来？
kb_root 指向知识库，撰写中实时核验
QAI 撰写速度这么快，质量跟得上吗？
速度来自 AI，质量来自流程：审计前置给事实基准、存疑即审计管过程、M-22+diff 管结果——三道防线与速度无关。
Q存量系统的规格书能补写吗？
可以。audit 先对存量源码建快照，撰写以快照为事实基准反向补全，验收标准不变。
Q多个需求并行会冲突吗？
每个需求独立项目目录与 config，编号区间隔离；link 检查兜住跨文档冲突。
