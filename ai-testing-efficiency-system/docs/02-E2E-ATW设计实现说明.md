# 02｜E2E-ATW 设计实现说明

> 本文说明 E2E-ATW 如何将需求材料转化为可执行、可核验、可复核的 UI 自动化交付。重点不是公开源码，而是解释架构、状态、契约、证据与失败治理的实现机理。
>
> 治理总览见 [01](01-体系设计总览.md)；完整质量闸门见 [03](03-治理机制与质量闸门.md)。

---

## 1. 定位与版本口径

E2E-ATW 是需求驱动的 UI 自动化测试工作台：输入**需求文档、规格说明书、代码仓库、数据口径、业务知识库**，经过解析、用例生产、环境预检、执行、数据实证、失败分类和报告闸门，形成可归档、可离线复核的交付物。

它的目标不是“让 AI 自由写脚本”，而是：

- 机械环节全脚本化；
- AI 只在受限语义工序中生产 draft；
- 产物必须经过 Schema、规则和证据验收；
- 报告数字必须能回到当次运行产物重算；
- 业务缺陷和高风险语义必须保留人工复核。

### 1.1 版本说明

公开演示站的 E2E 页面是 V2.2 快照，展示 21 道闸门；后续源工程契约扩展到 30 道，新增或强化了报告导航、自包含、业务语言、取样独立性、报告基线、定位链健康、断言强度、AI 成本和状态迁移覆盖。

本文按机制演进说明 30 项检查意图，但不混用不同版本的脚本数、Schema 数或验收成绩。实际项目以当版 `contract.json`、Schema 注册表和 `--print-checks` 输出为权威。

## 2. 总体架构

| 层 | 核心职责 | 关键设计 |
| --- | --- | --- |
| 契约层 | 统一规则、阈值、词表、闸门和预算 | `contract.json` 单一来源，向 lint/precheck/gate 分发 |
| 编排层 | 驱动八阶段、依赖、缓存、条件阶段与断点 | 唯一正式入口，gate 失败即终止 |
| 状态层 | 管理 Schema、运行游标、产物版本和原子写 | `run_dir` 是单次运行事实源 |
| 信任层 | 绑定产物、报告、证据和 claims | manifest 链式哈希 + attestation + 离线复核 |
| 能力层 | 用例生产、执行、核验、归因、知识和报告 | 生成与验收分离，AI 三段式 |

外部通道主要包括浏览器自动化和 DB 只读查询。通道只提供事实与执行能力，不自行决定业务验收结论。

### 2.1 数据流主线

```text
五源输入
  → 解析结果与规则资产
  → 用例 CSV / spec / 覆盖矩阵 / AI brief
  → run_dir（执行结果、台账、证据、归因）
  → 数据核验与失败分类
  → 报告、manifest、attestation
  → G 闸门与离线复核
  → 回归、指纹、定位策略和知识回流
```

## 3. 编排层：八阶段流水线

代码差异探测可作为可选前置阶段，用于补充代码源测试点；正式主流程保持八阶段。

| 阶段 | 输入与机器动作 | 主要输出 | 阻断语义 |
| --- | --- | --- | --- |
| `parse` | 解析需求、规格、代码、数据与知识边界 | 规则、导航、测试点、解析警告 | 输入不可用则不进入生成 |
| `gen` | 生成用例、执行圈、覆盖矩阵和断言 brief | CSV、spec、brief、coverage | 静态规则 FAIL 则不继续 |
| `precheck` | 检查运行时、浏览器、DB、目标环境和安全基线 | 预检记录 | 硬闸失败即停止 |
| `run` | 探针、只读圈执行、证据和遥测 | 执行结果、失败证据、定位与耗时数据 | 环境异常进入确认或熔断 |
| `run_write` | 按条件执行写链，管理快照和台账 | 写链结果与数据台账 | 无写链可跳过，遗留检查不可跳过 |
| `verify` | 执行只读数据核验计划 | 核验结果与异常明细 | unknown 不得记为 ok |
| `classify` | 按指纹和规则分类失败 | 分类结果、待复核项 | 分类异常或业务未复核不得归档 |
| `report` | 生成报告、执行 G 闸门、登记 claims | MD/HTML 报告、证据清单 | 任一硬闸 FAIL 禁止归档 |

### 3.1 引擎语义

- **唯一入口**：正式运行由编排器驱动，单个 CLI 只用于调试，避免口头串联造成跳步。
- **依赖校验**：阶段只消费声明过的上游产物，缺失或版本不符即失败。
- **缓存级联失效**：输入内容未变才可复用；上游变化必须使下游相关缓存失效。
- **断点续跑**：从明确阶段恢复，状态游标可追踪，不能借续跑绕过硬闸。
- **条件阶段**：条件谓词使用白名单，未知条件直接拒绝，而非默认跳过。
- **原子报告阶段**：报告生成与闸门验收作为一个交付单元，未绿报告不得归档。

## 4. 状态层：Schema 与 run_dir SSOT

### 4.1 run_dir 是运行事实源

```text
run_<timestamp>/
├── run_result.json          # 执行终态、统计与失败明细
├── verify_result.json       # 数据实证结果
├── classify_result.json     # 失败分类与复核状态
├── data_ledger.json         # 数据准备、使用与清理台账
├── triage/                  # 失败证据包和归因 draft
├── evidence/                # 截图、trace、日志等
├── manifest.json            # 产物摘要与链式哈希
├── attestation.json         # 报告 claims 与来源
└── report/                  # 与本次运行绑定的报告
```

报告只能绑定一个明确运行链，不能从历史目录中挑选“好看”的产物重新组合。补跑只更新其负责的用例事实，最终仍须重新生成并对账报告。

### 4.2 Schema 注册与迁移

- 新增结构化产物前先注册名称、版本和字段约束。
- 读写两侧统一校验，错误定位到具体字段，不做静默类型转换。
- 产物元数据记录 Schema、版本、生产者、运行标识、内容摘要和创建时间。
- 历史产物通过显式迁移函数升级，禁止读取时靠猜测兼容。
- 写入采用临时文件加原子替换，避免半成品被下游消费。

## 5. 契约层：规则只维护一份

### 5.1 三通道分发

| 通道 | 最早反馈时点 | 典型检查 |
| --- | --- | --- |
| lint | 用例或文档生成后 | 定位写法、固定等待、双轨断言、文件命名、禁用表述 |
| precheck | 执行前 | 环境、快照、平台一致性、只读通道、知识基线、预算配置 |
| gate | 报告与归档前 | 结构、覆盖、证据、claims、报告基线、成本与状态覆盖 |

一条规则放在哪里，取决于**最早可以在哪个阶段被确定性判定**。能静态发现的问题不留到整轮执行结束后。

### 5.2 契约治理要求

- 规则、阈值、词表和预算来自同一事实源；
- 检查项增删后，权威清单由工具同步生成；
- 软闸、硬闸、豁免和历史兼容策略必须显式区分；
- 豁免要有理由和适用范围，不能用全局关闭代替治理；
- 文档中的数量是快照，不能反向覆盖注册表。

## 6. AI 三段式：备料、draft、机器验收

### 6.1 通用约束

1. 机器从已授权输入中生成最小备料 brief；
2. AI 只能按指定 Schema 输出 draft；
3. 验收器检查结构、引用、枚举、证据路径和规则底线；
4. 通过后写入 `gated_at + draft_hash`，下游消费前重新计算摘要；
5. 内容变化、无戳或戳不匹配即拒绝；
6. 业务高风险结论仍需人工复核。

定位建议属于特殊的受限 AI 产物：它不凭验收戳直接入库，而是必须经过唯一匹配、可交互和位置复验后才能单次消费，再按人工与知识流程沉淀。

### 6.2 AI-01：断言生成

**备料**：规则、导航、数据样例、交互模式和历史坑点。

**AI 工作**：生成 UI 断言、DB 断言和边界值说明。

**机器验收**：

- UI 与 DB 双轨配对；
- 写链断言限定本轮时间窗，或显式登记豁免；
- 引用必须在备料或真实资产中存在；
- 恒真断言进入黑名单或降级；
- 批失败率超阈值时停止自动处理并转人工检查备料质量。

### 6.3 AI-02：失败归因

**备料**：用例元数据、错误摘要、DOM、截图、trace、DB 上下文、历史指纹和知识。

**AI 工作**：在固定根因枚举内给出建议、证据引用和修复建议。

**机器验收与成本护栏**：

- 证据必须引用证据包中的真实字段路径；
- 已命中可靠历史指纹的失败优先复用诊断，不重复调用 AI；
- 业务缺陷强制 `pending_review`；
- 低置信知识只进入待确认，不自动成为正式规则。

### 6.4 AI-03：覆盖语义判定

机器覆盖与语义忠实分开：

| 口径 | 含义 |
| --- | --- |
| `covered` | 规则已登记用例 |
| `verified` | 最近执行存在通过记录 |
| `faithful` | 断言在语义上真正实现规则要求 |

AI 可判为 `faithful / weak / wrong / unverifiable`，但机器底线可以强制降级；独立抽判用于防止自评自夸。无法判断的内容不得进入忠实覆盖率分母，更不能被当成通过。

## 7. 信任层：证据链与 claims 对账

### 7.1 四层机制

1. **manifest**：登记产物路径、SHA-256、生产者和阶段。
2. **chain_hash**：将前一环摘要、当前产物摘要和阶段绑定，识别增删、替换与换序。
3. **attestation**：登记报告数值声明及其源产物字段，绑定输入和报告摘要。
4. **离线复核**：独立重算文件摘要、链式哈希和 claims，不依赖原执行环境。

核心关系可表示为：

```text
chain_hash = sha256(previous_chain + artifact_sha256 + stage)
claim_value = recompute(source_artifact, source_field_path)
```

真实实现还需路径约束、Schema、原子写和审计；上述表达只说明机理。

### 7.2 五类攻击样本

| 样本 | 典型手法 | 防御点 |
| --- | --- | --- |
| 陈旧数据 | 旧 run、旧证据或局部迭代圈冒充发布结果 | 新鲜度、执行链绑定、全量发布口径 |
| 篡改产物 | 改数、删文件、换序、替换证据 | 文件摘要与链式哈希 |
| 数值虚报 | 报告数字与明细不一致 | claims 独立重算 |
| 引用幻觉 | 引用不存在的字段、文件或证据 | 引用存在性和摘要检查 |
| 断言脱钩 | 断言恒真、旧数据存在性、取样同源 | 时间窗、双轨、独立取样、变异探测 |

每次封版都应执行攻击样本拦截回归与发布准入检查。不同版本的攻击样本数量和成绩只在各自版本上下文内解释。

### 7.3 威胁边界

哈希链主要防御意外陈旧组合、事后修改和交付物替换，不能独立防御拥有高权限并愿意系统性重算整条链的恶意操作者。跨组织或高安全场景需要额外签名、只追加存储、独立日志与权限分离。

## 8. 执行器：效率、隔离与失败治理

### 8.1 探针与读写分圈

- 执行前检查登录、菜单可达、DB 通道和目标环境健康，探针失败不启动全量。
- 只读圈可并行，写链按项目契约串行或受控隔离执行。
- 写链执行前准备快照，数据按账号、业务标识或范围隔离，结束核对清理台账。
- 截图、trace、错误摘要和上下文与失败用例绑定，不只保留最后一条控制台错误。

### 8.2 失败五分类

| 分类 | 含义 | 处置 |
| --- | --- | --- |
| `env` | 环境或通道故障 | 二次确认、恢复环境，不直接归因产品 |
| `case-infra` | 定位、等待、断言等用例工程问题 | 修用例工程并回归 |
| `case-data` | 数据污染、过期或前置不满足 | 修数据与准备流程 |
| `case-deps` | 上游任务、单据链或外部依赖断裂 | 修依赖并记录卡点 |
| `biz` | 排除上述因素后的疑似业务缺陷 | 强制人工复核后进入缺陷流程 |

环境判定需要二次确认；重试使用白名单，账户锁定等故障不能通过重试放大。复跑用于确定性分类，不删除首次失败事实。

### 8.3 熔断、挂起与恢复

连续同类环境失败达到阈值后停止调度新用例，保存检查点，通过只读健康探针判断恢复。恢复后从明确状态续跑；预算耗尽则保留已完成和待续清单，不将残缺执行包装成全量完成。

### 8.4 调度与慢文件治理

- 按历史耗时进行最长处理时间优先（LPT）装箱，降低长尾等待；
- 上轮失败和 flaky 用例优先，缩短问题反馈时间；
- 慢文件进入 TopN 治理，标记在再生成时保留；
- 调度只改变执行顺序，不改变报告统计和发布口径。

## 9. TIA 与状态覆盖

### 9.1 测试影响分析（TIA）

TIA 复用“代码文件 → 代码测试点 → 用例 → 规格”的追溯链，将变更映射为迭代期执行范围：

- 映射链必须可溯源，断链即失败；
- 零映射、公共横切变更或无法证明安全时回退全量；
- 迭代圈带有明确标记，不生成发布口径报告；
- 发布前必须执行全量链兜底，防止影响分析漏判被隐藏。

### 9.2 状态迁移覆盖

轻量状态模型从用例、规格和知识候选中提取，但必须经人工确认，不能由 AI 凭空创造状态机。模型驱动迁移用例生成和覆盖计算：普通缺口按契约披露，关键业务或财务迁移缺失可设为硬阻断。

历史趋势只追加可机器对账的数字，并绑定报告与数字摘要；摘要不符时拒绝追加，防止趋势被事后修改。

## 10. 定位体系与断言强度

### 10.1 确定性优先的定位链

| 层级 | 机制 | 边界 |
| --- | --- | --- |
| 稳定策略链 | 按成本与稳定性选择 role/testid/css 等策略 | 遥测记录命中层级与耗时 |
| DOM 指纹降级 | 结构相似度达到阈值后才尝试历史成功策略 | 低于阈值直接失败，不盲目重试 |
| 视觉建议 | 默认关闭，显式开启后由 AI 给定位建议 | 禁坐标、严格预算、三重复验、写链默认禁用 |

同一元素反复依赖视觉兜底时应转人工治理，而不是让模型成为永久运行时依赖。跨运行的定位遥测用于识别脆弱策略和异常波动。

### 10.2 断言强度

“存在断言”不等于“能捕获错误”。断言强度自检可使用：

- 比较符翻转；
- 期望值扰动；
- 冗余断言识别；
- 取样独立性检查；
- 业务规则与断言对象映射。

强度不足、冗余或缺少自检产物时按契约 WARN 或 FAIL，防止全绿报告建立在恒真断言上。

## 11. 数据体系

### 11.1 数据核验

常见核验类型包括平衡、多结果匹配、比例拆分、派生存在、字段链和规则追踪。写链必须证明数据属于本轮，而不是在全历史中找到一个“看起来像”的记录。

### 11.2 三态台账

- `ok`：已执行且满足明确断言；
- `fail`：已执行且违反断言；
- `unknown`：未执行、不可达、超时或证据不足。

`unknown` 不能算成功，也不能被“零遗留”表述掩盖。危险清理由授权策略决定，优先业务作废或受控测试卫生流程，不能为了台账好看而越权删数。

### 11.3 共享只读通道

连接和账号只读、SQL 白名单、参数化、表到库定位、结果截断和全量审计在通道内统一实现。E2E、缺陷定位和专项核验复用同一安全底座，避免每个工具各自实现一套权限规则。

---

## 12. 知识与成本运营

### 12.1 三层知识模型

- 框架层：跨项目通用交互、指纹和坑点；
- 平台层：特定平台共享规则；
- 项目层：本项目业务特例与数据漂移史。

加载时就近覆盖，项目特例不反向污染框架规则。条目包含证据、置信、命中与失效记录；长期未命中可降置信或休眠，新指纹和低置信内容先进入 provisional 或 pending_review。

### 12.2 经验回流

- 定位成功策略回流定位链；
- 人工确认的失败分类回流指纹；
- 业务缺陷回流回归用例与业务知识；
- 闸门失败修复后可沉淀新检查或防错提示；
- 知识入库始终保留证据与人工边界，避免噪声自动固化。

### 12.3 AI 成本台账

AI-01/02/03 的验收产物与成本事件绑定，审计产物摘要、预算状态和漏记情况。没有可靠 token 数据时保留原始可核验口径，不做虚构换算。成本用于优化流程与预算，不直接作为效能收益。

## 13. 报告与 G 闸门

报告至少包含执行范围、结果、失败明细、证据索引、未知与豁免、覆盖、边界和复核信息。报告生成后必须执行当版 G 闸门。

| 分组 | 防护重点 |
| --- | --- |
| G-01～G-08 | 结构、编号、状态、证据、汇总与报告基本形态 |
| G-09～G-12 | 覆盖、映射、数据台账与基线 |
| G-13～G-16 | 新鲜度、引用、claims 与 flaky |
| G-17～G-21 | 转化、专项核验、截图、代码覆盖与 TIA 链 |
| G-22～G-26 | 导航、自包含、业务语言、独立取样与报告基线 |
| G-27～G-30 | 定位健康、断言强度、AI 成本与状态迁移 |

完整 30 项检查意图、硬软门说明和攻击映射见 [03-治理机制与质量闸门](03-治理机制与质量闸门.md)。

## 14. 安全与适用边界

### 14.1 安全底线

- 秘密信息通过受控配置注入，不进入仓库、提示词或报告；
- 生产和测试配置分离，生产核验默认只读；
- 知识权威区只读，可回写区域按流程控制；
- 写链只在授权环境执行，具备快照、隔离与台账；
- 公开证据去除客户数据、内部拓扑和真实业务标识。

### 14.2 不覆盖的范围

- 不替代真机与完整兼容性矩阵；
- 不将耗时遥测当成性能压测；
- 不将报告防篡改当成安全渗透测试；
- 不承诺业务语义完全无人复核；
- 不承诺局部执行等价于全量发布验收；
- 不承诺机器全绿等于业务风险为零。

### 14.3 持续校准事项

- 用例转化档位与部分启发式规则；
- 历史项目基线和旧产物迁移；
- 同环境性能、并发与资源消耗复测；
- 定位健康、断言强度、语义判定稳定性和成本收益趋势。

旧版本中的已修复缺口不应继续写成当前限制；未在新材料中验证的能力也不应写成既成成果。
