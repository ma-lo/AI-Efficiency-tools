> 本文帮助管理者、质量角色、工程角色和初次接触 AI 工程化的读者理解：为什么这些机制组合起来有效，以及文档中的术语应如何准确解释。

# 上篇｜体系原理

## 1. 概率性语义与确定性工程必须分工

大语言模型擅长理解、归纳和生成自然语言，但输出具有概率性。“看起来合理”不等于“事实正确”，同一输入也可能产生不同结果。

传统软件工程则擅长确定性执行：结构校验、哈希、统计、对账、状态转移和权限判断都可以被重复验证，但不擅长独立理解模糊业务语义。

本体系将两类能力放在各自合适的位置：

```text
需求理解、断言草拟、失败研判、覆盖语义 → AI 提供 draft
结构、事实、引用、权限、统计、证据、流程 → 机器确定性验证
```

体系可靠性不取决于“模型是否每次都聪明”，而取决于**错误能否被下游机制发现和隔离**。

---

## 2. 生成与验收分离：写的人不能自己判卷

如果同一个 AI 或同一个执行者既生成结果，又决定结果是否合格，流程就缺少独立约束。即使多数时候正确，也无法证明例外会被发现。

生成与验收分离包含三层：

1. **职责分离**：生产工具只生成，验收器只按规则判断；
2. **数据分离**：AI 只能写 draft，正式产物由机器验收入库；
3. **内容绑定**：验收后记录 `gated_at + draft_hash`，内容改变即失效。

人工反向确认仍然存在，但它用于业务取舍和高风险语义，不替代机器检查；机器检查也不替代人的岗位责任。

---

## 3. 受控 RAG：不是资料越多，结论越可靠

将几十份资料一次性提供给模型，可能带来注意力稀释、版本冲突和无依据拼接。受控 RAG 的重点是**事实围栏与最小备料**：

- 只检索当前任务需要的授权资料；
- 优先使用经过实证的知识和代码审计结果；
- brief 中保留来源、范围和缺项；
- AI 只能基于备料生成指定 Schema 的 draft；
- 引用与事实由机器核验，无法确认的进入待确认。

RAG 负责“给 AI 合适的材料”，验收器负责“判断产物能否被消费”，两者不能互相替代。

---

## 4. Agent 编排：自由必须被流程和权限包围

Agent 能规划与调用工具，但规划结果不应自动获得流程和权限正确性。可靠编排需要：

- 唯一入口和明确状态机；
- 上游产物的 Schema、版本和验收凭证；
- 每个工具的输入、输出与权限边界；
- FAIL 回退位置和最大修复轮次；
- 高风险节点的人工确认；
- 完整审计与可恢复状态。

因此，AI 是工序中的执行者，不是裁判，也不是安全边界。

---

## 5. 契约化与 SSOT：规则不能只靠“记得同步”

同一规则如果同时写在提示词、脚本、检查器和 Wiki 中，版本漂移只是时间问题。单一事实来源（SSOT）要求：

```text
contract.json
  ├─→ lint：生成后尽早检查
  ├─→ precheck：执行前检查
  └─→ gate：交付前检查
```

修改规则只改变契约和对应实现，消费通道从同一来源获取。Schema 注册表、检查注册表和知识事实源也遵循同一原则。

SSOT 不意味着“所有信息只存一份物理文件”，而是**同一类事实只有一个权威来源，其他位置引用或派生，且可以追踪**。

---

## 6. 可证伪：从信任执行者转向验证产物

可信报告需要回答四类问题：

| 问题 | 机制 |
| --- | --- |
| 数据从哪里来 | run_dir、证据索引、时间窗与执行链 |
| 文件有没有被换过 | SHA-256 与链式哈希 |
| 报告数字是否一致 | claims 从源产物独立重算 |
| 断言是否真的能捕获错误 | 双轨、独立取样、语义覆盖与变异探测 |

“可证伪”不是要求所有结论都必须为真，而是要求每个结论都有明确的验证方式。无法验证的内容应标为 unknown 或待确认，而不是被语言包装成确定事实。

哈希链能够提高事后修改被发现的概率，但不等于数字签名，也不能独立防御拥有高权限并重算整条链的恶意操作者。

---

## 7. 双轨断言与独立取样：避免循环证明

页面表现和数据库事实分别反映不同侧面：

- UI 成功但 DB 未变化，可能是假成功；
- DB 有目标数据但属于历史记录，也不能证明本轮成功；
- 用准备数据的前提作为断言依据，会形成同源恒真。

因此需要本轮时间窗、业务标识、独立取样和必要的状态链核验。双轨的价值不是“多写一条断言”，而是建立**相互独立的事实约束**。

---

## 8. 失败分类：把有限注意力投向正确问题

自动化失败可能来自环境、用例工程、测试数据、上下游依赖或真实业务缺陷。如果不分类，团队会在假失败中消耗大量时间，也可能把真缺陷误归为环境抖动。

五类失败对应不同责任与处置：

- `env`：恢复环境并二次确认；
- `case-infra`：修定位、等待和断言；
- `case-data`：修数据准备、隔离与清理；
- `case-deps`：修上游链路与依赖；
- `biz`：人工复核后进入业务缺陷流程。

失败复跑只帮助判断确定性，不能删除首次失败。历史指纹可以复用，但新证据允许推翻旧分类并留下审计记录。

---

## 9. 知识复利：每次工作都为下一次降本

单点工具的收益往往随使用次数线性增长，知识体系则可能产生复利，但前提是经验能够被验证、消费和保鲜：

- 缺陷回流回归用例，防止再次发生；
- 失败分类回流指纹，减少重复研判；
- 定位经验回流策略链，降低维护成本；
- 业务规则回流知识库，改善下一次生成；
- 闸门问题回流检查规则，防止流程再次失守。

知识入库必须保留人工闸和证据要求。未经核验的自动学习只会更快地固化噪声。长期未验证的知识需要降置信、休眠或淘汰。

---

## 10. 效能治理：局部提速不等于组织提效

一个工具让某人生成文档快了三倍，不代表需求交付周期一定缩短。等待、返工、评审、环境、失败研判和发布确认可能仍然占据主要时间。

效能治理需要同时观察：

- **流动**：需求从提出到交付的总时长与等待结构；
- **质量**：缺陷、返工、变更失败和重复问题；
- **可信**：证据、对账、未知与例外；
- **采用**：真实项目使用、流程完成和人工绕行；
- **复利**：知识、规则和回归资产是否被复用；
- **成本**：工具维护、模型调用和人工复核投入。

只有收益能够跨项目、跨周期复现，并且质量和风险没有恶化，才能称为组织级效能提升。

# 下篇｜术语表

## A. 治理与质量

| 术语 | 准确含义 |
| --- | --- |
| 效能治理 | 通过流程、工具、度量、知识和组织机制，持续改善产研交付效率、质量与可预测性的管理工作。 |
| 质量左移 | 将风险识别和质量约束前移到需求、设计与编码阶段，减少后期返工。 |
| DI | 本项目历史质量指标名称。具体缺陷范围、权重和公式以对应统计制度为准，不与其他组织的 DI 直接比较。 |
| 缺陷逃逸率 | 在既定统计口径下，流出到生产或后续阶段的缺陷占比。必须明确时间窗、严重度和去重规则。 |
| 缺陷检测率 | 在既定统计口径下，发布前或指定阶段发现缺陷的占比。与逃逸率只有在同队列、同分母等条件满足时才可能形成特定数学关系。 |
| SLA | 对服务或交付目标的约定，如响应时限或完成时限；具体含义以对应协议为准。 |
| RACI | 角色分工方法：R 执行、A 最终负责、C 协商参与、I 知会。 |
| 同类项目队列（cohort） | 在相同范围与统计规则下被持续观察的一组项目、需求或版本，用于避免跨口径比较。 |
| E2E | 端到端测试，从用户入口到业务结果验证多个组件协同工作的过程。 |
| 回归测试 | 变更后重跑既有验证，确认原有能力未被破坏。 |
| 冒烟测试 | 用最小核心链路快速判断版本是否值得进入进一步测试。 |
| flaky | 同一用例在条件未明确定义变化时表现不稳定，需要分类和治理，而非简单重跑隐藏。 |

## B. AI 与自动化工程

| 术语 | 准确含义 |
| --- | --- |
| LLM | 大语言模型，擅长语义理解和生成，但输出具有概率性，需要外部事实与验收约束。 |
| Prompt | 提供给模型的任务指令。它是软约束，不能替代权限、流程和机器校验。 |
| RAG | 检索增强生成。先检索资料再生成；受控 RAG 还需来源、范围、引用和验收边界。 |
| AI Agent | 能规划并调用工具完成任务的 AI 执行单元，需要在状态机和权限边界内运行。 |
| SKILL.md | 技能说明与触发入口，可描述输入、流程和约束；关键规则仍应落在工具与契约中。 |
| brief | 机器为特定语义任务准备的最小事实包，包含必要来源、上下文和限制。 |
| draft | AI 生成的待验收草稿，不是可直接交付或入库的正式产物。 |
| `gated_at` | 记录 AI 产物通过验收的时间。需与内容摘要一起使用才有绑定意义。 |
| `draft_hash` | 对去除验收戳后的 draft 稳定序列化并计算的摘要，用于识别验收后内容变化。 |
| `pending_review` | 等待人工复核的状态，不能按已通过或已关闭处理。 |
| Schema | 结构化产物的字段、类型和版本契约，读写两侧均可据此校验。 |
| Playwright | 浏览器自动化执行框架，本体系将其作为 UI 执行通道之一。 |
| 定位器 | 自动化脚本识别页面元素的策略或表达式，需要稳定性和健康度治理。 |
| 视觉兜底 | 在确定性定位失效后使用视觉或模型建议的受控降级方式，默认关闭且需复验。 |

## C. 可信执行与质量闸门

| 术语 | 准确含义 |
| --- | --- |
| 假绿（False Green） | 实际未满足验收条件，报告却显示通过或全绿的现象。 |
| 质量闸门（gate） | 流程中的机器检查点。硬闸失败阻断交付，软闸用于风险披露，二者需区分。 |
| run_dir | 一次运行的事实目录，保存结果、证据、台账、报告和复核信息。 |
| SSOT | 单一事实来源。同一类事实只有一个权威来源，其他位置引用或派生。 |
| SHA-256 | 将内容映射为固定长度摘要的算法，可用于识别内容变化，但不等同于身份签名。 |
| 链式哈希 | 将前一环、当前产物和阶段绑定，帮助发现增删、替换和换序。 |
| claims | 报告中需要验证的结构化数值或结论声明，例如执行数、通过数和失败数。 |
| attestation | 将 claims 与源产物、来源字段和摘要绑定，供独立复核的机制。 |
| 离线复核 | 不重新执行业务测试，独立检查文件摘要、证据链和报告 claims。 |
| 攻击样本 | 故意构造的陈旧、篡改、虚报、幻觉或脱钩样例，用于验证防御能否拦截。 |
| 双轨断言 | 使用 UI 表现与数据事实两类证据共同验证业务结果。 |
| 独立取样 | 断言所需证据不直接由被断言前提自身提供，避免循环证明。 |
| 变异探测 | 有意改变比较符、期望值或输入，验证断言是否能捕获错误。 |
| 三态台账 | 将数据或核验状态区分为 ok、fail、unknown，禁止把未知当成功。 |
| TIA | 测试影响分析，根据变更与追溯关系选择迭代期测试范围；发布仍需全量兜底。 |
| LPT | 最长处理时间优先的调度策略，用于降低并行执行长尾，不改变测试结论。 |

## D. 知识与运营

| 术语 | 准确含义 |
| --- | --- |
| 知识复利 | 将一次工作沉淀为可复用资产，使后续生产、执行和研判成本持续下降。 |
| 知识分层 | 按框架、平台和项目组织知识，并在加载时就近覆盖，避免特例污染通用规则。 |
| 知识保鲜 | 通过实证日期、命中、复核和版本记录维持知识有效性。 |
| 置信衰减 | 对长期未验证或反复失效的知识降低可信度，必要时休眠或归档。 |
| 失败指纹 | 对错误类型、摘要和上下文的稳定特征化，用于复用历史分类和诊断。 |
| 工具组合治理 | 对工具的引入、使用、维护成本、收益、合并和退出进行持续管理。 |
| 人工绕行率 | 流程未通过既定工具链完成的比例，用于发现工具不适用、采用不足或例外失控。 |
| 虚荣指标 | 看起来增长但无法证明有效交付的指标，如生成量、调用量或知识条目数。 |
| 脱敏 | 移除或替换公司、客户、项目、环境、凭据和业务数据等敏感信息，同时保留可理解的机制。 |
