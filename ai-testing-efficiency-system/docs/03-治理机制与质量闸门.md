# 03｜治理机制与质量闸门

> 本文从质量治理与可信交付角度说明：如何防止 AI 和自动化产生“看起来完成、实际上无法证明”的产物，以及效能治理经理如何把这些机制嵌入组织流程。
>
> 体系治理见 [01](01-体系设计总览.md)；E2E 实现机理见 [02](02-E2E-ATW设计实现说明.md)。

---

## 1. 为什么“全绿”仍然可能不可信

一次典型的假绿并不意味着有人故意造假，也可能是流程自然失控：

- 执行失败，但报告读取了上一轮成功产物；
- 页面显示成功，后台数据却没有按预期变化；
- 报告数字被汇总错误放大，明细与结论不一致；
- AI 引用了不存在的证据或把推断写成事实；
- 断言永远为真，无法捕获业务错误；
- 局部影响分析运行被包装成全量发布结果。

因此，质量治理不能只看“有没有报告”，而要验证：

1. 报告是否属于本次执行；
2. 证据是否真实、完整且未被替换；
3. 数字能否从源产物重算；
4. 断言是否真正对应业务规则；
5. 未知、豁免和人工复核是否被如实披露。

## 2. 三层可信防御

### 2.1 第一层：契约化规则

`contract.json` 统一维护闸门、lint、precheck、词表、阈值和预算，避免提示词、脚本与文档各自漂移。

- 能在生成后发现的问题进入 lint；
- 能在执行前判断的问题进入 precheck；
- 必须结合完整产物判断的问题进入 gate；
- 权威检查清单由注册表输出，文档不反向覆盖工具。

### 2.2 第二层：证据链

- 每次运行使用独立 `run_dir`，报告与运行链绑定；
- manifest 登记文件 SHA-256、生产者和阶段；
- chain_hash 识别产物增删、替换和换序；
- attestation 将报告 claims 绑定到源产物字段；
- 离线复核器独立重算，不依赖执行者自证。

### 2.3 第三层：硬闸门与人工终审

硬闸失败必须阻断归档，不能通过口头确认跳过。软闸用于提示风险和推动改进，但必须与硬闸分开统计。机器通过只表示满足已定义规则，业务风险接受、重大缺陷和发布取舍仍需责任人终审。

## 3. AI 产物的准入机制

AI 只承担有限语义工作，其产物遵循：

```text
机器备料 brief
  → AI 生成 draft
  → Schema / 引用 / 枚举 / 证据 / 规则底线验收
  → gated_at + draft_hash
  → 下游复核摘要后消费
  → 高风险业务语义人工复核
```

关键约束：

- 无戳、戳不匹配或内容被修改，下游拒绝消费；
- AI 不得直接修改正式产物或最终报告；
- 证据引用必须指向真实备料字段或文件；
- 自动修复设置上限，超限后停机报告；
- 验收戳证明“曾通过检查”，不证明业务语义绝对正确；
- 业务缺陷、低置信知识和重大风险进入 `pending_review`。

## 5. 攻击样本：验证闸门真的会拦

正常路径通过只能证明系统能运行，不能证明防御有效。每次重大机制升级都应构造攻击样本并验证拦截。

| 攻击类型 | 示例手法 | 预期防御 |
| --- | --- | --- |
| 陈旧数据 | 修改时间、复用旧 run、用局部圈替代全量 | G-13、运行链绑定、发布口径 |
| 篡改产物 | 改数字、删文件、换序、替换证据 | manifest、chain_hash、G-14 |
| 数值虚报 | 通过率写成 100%，汇总大于明细 | G-05、G-15、离线重算 |
| 引用幻觉 | 引用不存在的证据或字段 | G-04、G-14、AI 验收器 |
| 断言脱钩 | 全历史存在性、恒真断言、同源取样 | 时间窗、G-25、G-28、双轨断言 |

攻击样本结果必须绑定版本、范围和执行记录。不同历史验收中的 14、16 或其他样本数量不能合并成一个长期“100% 安全”宣传口径。

## 6. 失败治理：先分类，再处置

执行失败不等于产品缺陷。统一使用五类根因：

| 分类 | 判定依据 | 处置与质量口径 |
| --- | --- | --- |
| `env` | 探针、网络、通道或服务环境异常 | 二次确认并恢复，不直接归责版本 |
| `case-infra` | 定位、等待、断言或用例工程错误 | 修用例并回归，不计为业务缺陷 |
| `case-data` | 数据污染、过期或前置不足 | 修数据准备与隔离机制 |
| `case-deps` | 上游任务、单据链或外部依赖断裂 | 修依赖并记录链路卡点 |
| `biz` | 排除其他类别后的疑似业务问题 | 强制人工复核，确认后进入缺陷流程 |

补充纪律：

- 环境重试使用白名单，不能用重试放大账户锁定等故障；
- flaky 复跑只用于分类，不删除首次失败事实；
- 已确认的历史指纹可以复用，但新根因能够推翻旧分类并留下记录；
- 隔离或 quarantine 必须有原因和退出条件，不能成为隐藏失败的场所；
- 业务缺陷至少回流一条回归用例，必要时补充规则与知识。

## 7. 数据实证与证据分级

### 7.1 双轨与独立取样

UI 断言回答“用户看到了什么”，DB 只读核验回答“业务事实是否按预期形成”。两者互相印证，但不能简单使用同一前提互相证明。

- 写链数据必须限定本轮时间窗或业务标识；
- 取样来源与被断言值保持必要独立；
- 全历史存在性不能证明本轮操作成功；
- 数据库不可达时为 unknown，不得写 ok；
- 数据清理失败必须进入台账，不能为了全绿而删除失败记录。

### 7.2 证据使用原则

直接执行记录、运行时结果和文件摘要优先于模型推断。推断与未验证内容可以服务排查，但不能进入最终事实结论。证据不足时应输出“当前无法确认、还缺什么、下一步如何取得”，而不是补写一段听起来合理的解释。

## 8. 质量左移与岗位协同

| 阶段 | 机器准入 | 质量负责人 | 效能治理经理 |
| --- | --- | --- | --- |
| 需求与详设 | D/R 检查、引用溯源、评审结论 | 验收口径、风险与严重问题 | 将评审嵌入流程，度量返工和等待 |
| 规格与编码 | M/L 检查、契约对拍、编译与代码闸 | 覆盖与高风险变更复核 | 维护工具组合、范围与版本治理 |
| 测试生产 | T 检查、17 字段契约、覆盖矩阵 | 判断测试充分性 | 推动 AC/TR 同上游和资产复用 |
| 执行与核验 | 探针、双轨、台账、证据包 | 缺陷分类与业务复核 | 运营环境、成本、自动化健康 |
| 报告与发布 | G 闸门、claims、离线复核 | 风险接受与发布终审 | 确保例外留痕和指标可信 |
| 复盘与预防 | 回归、指纹、知识回流 | 审核改进有效性 | 管理 backlog、收益和推广 |

## 9. 安全、权限与审计边界

- 数据库连接与账号只读，危险操作在通道层拒绝；
- 参数化查询、结果截断、敏感字段最小化和全量审计；
- 写链仅在授权测试范围执行，快照、隔离和台账缺一不可；
- 秘密信息不进入仓库、提示词、证据包或公开报告；
- 知识权威区只读，自动学习不能直接改权威事实；
- 视觉兜底默认关闭，不因为追求自动化率而绕过安全策略；
- 哈希链不替代外部签名、独立日志、只追加存储和权限分离。

高安全场景应明确补充威胁模型，而不是把“有哈希”宣传为“不可篡改”。

## 10. 治理指标与反误导

| 指标 | 正确用途 | 常见误用 |
| --- | --- | --- |
| 硬闸通过率 | 观察交付物达到机器底线的比例 | 通过降低规则或增加豁免制造提升 |
| 证据完整率 | 检查结论是否有可复核依据 | 只统计文件存在，不检查时效和摘要 |
| claims 对账 | 验证报告数字与源产物一致 | 用同一错误汇总逻辑生成和对账 |
| unknown 占比 | 暴露证据与执行缺口 | 将 unknown 排除出分母或算作通过 |
| flaky 率 | 评估自动化健康和结论稳定性 | 通过复跑删除首次失败 |
| 断言强度 | 判断断言捕获错误的能力 | 用断言数量替代有效性 |
| 缺陷逃逸与检出 | 按既定口径观察质量结果 | 不同时间窗混算或直接宣称互补 |
| AI 成本 | 优化已验收产物的投入 | 用调用量代表效能收益 |

效能治理经理负责指标可运营，质量负责人负责质量口径与风险解释，两者都不能通过调整分母制造“改善”。
