# 01｜体系设计总览：从工具建设到效能治理

> 本文从**效能治理经理**视角回答：为什么建设、治理什么、如何形成体系、怎样推广和度量。质量负责人视角用于补充质量准入与可信交付。

## 1. 背景：效能瓶颈不只是执行速度

传统产研团队的低效往往被归因于“人不够”或“执行太慢”，但真实损耗分布在整个交付链：

1. **上游返工**：需求、详设和规格缺少统一契约，编码与测试阶段才发现歧义。
2. **中间搬运**：文档、用例、数据和报告由人工反复复制，工具之间没有稳定接口。
3. **下游不可信**：报告全绿与真实通过之间缺少证据绑定，团队仍需重复核验。
4. **失败高研判成本**：环境、数据、依赖、用例和业务缺陷混在一起，专家成为瓶颈。
5. **知识不复利**：经验停留在个人记忆或复盘文档中，人员变化后能力退化。
6. **工具采用不足**：新工具没有进入真实流程，也没有明确责任人、收益口径和退出机制。

AI 能降低语义生产成本，但也可能放大上述问题：生成越快，未经验证的文档、代码和结论扩散越快。因此，建设目标必须是**效率线与可信线并行，运营线从第一天介入**。

## 2. 治理目标与三条公理

### 2.1 治理目标

| 目标 | 管理含义 | 工程承载 |
| --- | --- | --- |
| 提效 | 减少机械生产、等待、搬运与重复研判 | AI 语义生产、流水线、缓存、调度与共享通道 |
| 增质 | 让问题更早暴露，减少返工和逃逸 | 质量左移、契约对拍、双轨断言与缺陷闭环 |
| 可信 | 让结论能够复核，而非依赖个人承诺 | 验收戳、证据链、claims 对账与硬闸门 |
| 可复制 | 新项目与新人可以按同一套方式工作 | 技能入口、项目初始化、模板、知识与培训 |
| 可运营 | 能衡量采用、收益、成本、风险和退化 | 指标树、成本台账、版本管理与组合治理 |

### 2.2 三条不可让渡的公理

1. **机械环节全脚本化**：能确定性计算的工作不交给概率性判断。
2. **AI 产物必经机器验收**：AI 只生成 draft，机器验收与内容绑定后才允许下游消费。
3. **一切结论可证伪**：每个关键数字可重算、每个引用可定位、每次运行可独立检查。

“成本闸门”是三项公理落地的约束：新机制必须可诊断、可维护、可审计；高维护成本且收益不清晰的能力应降级为可选增强，而不是为了技术先进性强推。

## 3. 体系架构：五层、四支柱、一张验收网

### 3.1 五层架构

| 层 | 职责 | 设计边界 |
| --- | --- | --- |
| 技能接入层 | 将自然语言意图路由到工具链 | 薄入口，不复制规则，不直接放行产物 |
| 工具执行层 | 承载详设、规格、编码、测试、数据与缺陷工作 | 每个工具独立演进，生成与验收分离 |
| 契约层 | 统一 Schema、编号、配置、版本与检查注册 | 规则只维护一份，清单机器生成 |
| 数据通道层 | 提供只读查询、参数化、截断、路由和审计 | 安全能力物理化在通道，不靠提示词约束 |
| 知识层 | 提供业务与 BI 事实、经验和项目特例 | 来源可核验，分层覆盖，人工控制入库 |

横切的**机器验收网**检查结构、事实、覆盖、证据、成本和安全，防止“单层合格、层间组合失真”。

### 3.2 四大支柱

- **工具链路化**：把流程固化为状态和准入，而不是把操作顺序写在提示词里。
- **受控 RAG**：机器先备料，AI 在事实围栏内做语义加工，机器再验收。
- **Agent 编排**：AI 是有限工序的执行者，不是流程裁判，也不是权限边界。
- **自积累成长**：缺陷、失败、定位和评审经验回流为回归、规则和知识资产。

## 4. 资产组合：11 个工程工具与双知识库

### 4.1 按产研链布点

| 产研阶段 | 工具组合 | 主要治理点 |
| --- | --- | --- |
| 详设与评审 | `prd-toolkit`、`rv-toolkit` | 一产一审、事实溯源、严重问题禁过 |
| 规格编写与验证 | `xx-spec-writing`、`spec-toolkit` | 编写层做薄，验证复用统一基座，前后端契约对拍 |
| 编码与单测 | `xx-spec-coding`、`unit-test-selfcheck` | 范围受控、人工反向确认、真实执行与归档证据 |
| 用例与执行 | `tc-toolkit`、`E2E-ATW` | AC/TR 同上游、17 字段契约、八阶段与可信报告 |
| 数据与缺陷 | `db-query-assistant`、`defect-hunter` | 共享只读通道、多源证据链、缺陷反哺 |
| 专项业务核验 | `depr-check-toolkit` | 多引擎、版本化模板、环境差异与归档 |

“13”在本体系中是**11 个工程工具 + 2 座知识库**，不是 13 个同类型工具，也不把项目级或专项技能重复计数。

### 4.2 双知识库

- **业务实现知识库**：业务流程、规则、状态、异常、联调、代码映射和待确认事项。
- **BI 系统知识库**：视图、字段、配置基线、常见问题和运行时核验依据。

知识不是静态附件，而是工具输入和治理资产。框架层、平台层、项目层就近覆盖；无法实证的内容进入待确认，不允许为了“知识库完整”而编造。

### 4.3 工具联动方式

工具间通过契约而非代码强耦合：

- 同款 `scope_report` 等 Schema 传递范围与测试点；
- 全局编号贯通规则、用例、缺陷和证据；
- DB 只读通道被 E2E、缺陷定位和专项核验复用；
- 规格编写复用规格验证基座；
- AC/TR 成为测试生产共同上游；
- 缺陷转化为回归用例、检查规则和知识条目。

## 5. 治理机制：让体系能被管理，而不只是能运行

### 5.1 流程治理

- 唯一入口和阶段依赖机器化，禁止通过对话口头跳步。
- 上游未验收，下游拒绝消费；例外必须记录原因、责任人和处置状态。
- FAIL 回到源资产修复，自动修复设置上限，超限停机并输出人工决策点。
- 机械阶段可无人值守，业务缺陷和高风险语义必须人工复核。

### 5.2 契约与版本治理

- `contract.json` 是规则事实源，向 lint、precheck、gate 分发。
- Schema 注册、版本迁移和原子写保证产物可兼容、可恢复。
- 检查清单由注册表输出，文档中的数量只作为版本快照。
- 不同版本的脚本数、Schema 数、闸门数和验收成绩不跨版本混算。

### 5.3 可信治理

- `run_dir` 是一次运行的事实源，报告与运行目录绑定。
- `manifest` 登记文件摘要与阶段链，`attestation` 登记报告 claims 的来源。
- 离线复核器重算文件哈希、链式哈希和 claims，不依赖执行者自证。
- 攻击样本验证陈旧数据、篡改、虚报、引用幻觉和断言脱钩能否真正被拦截。

### 5.4 知识治理

两条闭环必须区分：

1. **维护工作流**：收集 → 筛选 → 实证 → 映射 → 落笔 → 版本 → 报告。
2. **资产生命周期**：采集 → 核验 → 入库 → 引用 → 保鲜 → 休眠 → 淘汰。

低置信与模型推断先进入待复核；权威知识区与可回写区分离；缺陷复盘必须形成至少一种可消费资产。

### 5.5 成本与风险治理

- AI 成本事件与已验收产物绑定，不用调用次数代替收益。
- 重复失败优先复用指纹与历史确认，避免无意义重复调用模型。
- 数据库只读、结果截断、审计、秘密隔离和写链快照构成安全底线。
- 哈希链不替代高安全场景所需的签名、外部审计与权限分离。

## 6. 角色分工：效能主责，质量共治

R=执行，A=最终负责，C=协商参与，I=知会。

| 事项 | 效能治理经理 | 质量负责人 | 产品/研发负责人 | 平台或安全角色 |
| --- | --- | --- | --- | --- |
| 治理策略与工具组合 | A/R | C | C | C |
| 工具链建设与运营 | A/R | C | C | R |
| 质量标准与机器闸门 | R | A | C | C |
| 业务规则与验收口径 | C | R | A/R | I |
| 发布质量终审 | C | A/R | R | I |
| 权限、数据与安全 | C | C | I | A/R |
| 度量、复盘与改进 | A/R | R | C | C |

效能治理经理不替代业务和质量责任，而是确保流程、工具、证据、度量与改进闭环能够持续运转。

## 7. 度量体系：从产出量转向有效交付

| 维度 | 指标示例 | 需要防止的误导 |
| --- | --- | --- |
| 流动效率 | lead time、cycle time、等待、返工、按期交付 | 把生成量当效率，把局部提速当端到端提速 |
| 工具采用 | 活跃项目、流程完成、人工绕行、例外到期 | 把安装量、账号数或调用次数当真实采用 |
| 质量结果 | 缺陷密度、逃逸、检出、变更失败、重复缺陷 | 混用项目群、时间窗、严重度和去重口径 |
| 测试可信度 | 证据完整、claims 对账、陈旧拦截、未知占比 | 将 unknown 算通过，将软门结果混入硬门 |
| 自动化健康 | flaky、环境失败、定位脆弱、断言强度 | 用重跑后通过抹去首次失败 |
| 知识复利 | 命中、复用、新鲜度、休眠、回流完成 | 用知识条目数量替代知识有效性 |
| AI 成本 | 每个已验收产物成本、重试成本、预算超限 | 没有可靠数据时强行换算 token 或收益 |
| 风险合规 | 越权、敏感泄露、例外、审计完整 | 用平均效率收益抵消严重风险事件 |

### 7.1 历史综合结果

既有实践保留了以下脱敏趋势：线上缺陷密度下降 94%+，缺陷逃逸率 4.7% → 0.73%，缺陷检测率 75.5% → 88.4%，工具链承接重复性工作 60%+，迭代准时率 98%、SLA 100%。

这些是流程、团队、质量和工具共同作用的综合治理结果，**不能全部归因于 AI 工具体系**。检测率与逃逸率按各自历史口径呈现，不在缺少共同分母与同期队列时宣称互补。性能数据须在同环境复测后发布。

### 7.2 运营节奏

- 每日处理硬闸、环境、权限和业务复核异常；
- 每周分析采用、失败模式、修复轮次、慢步骤与成本；
- 每迭代复盘逃逸、返工、误报、flaky 和例外；
- 每月评估工具收益与维护成本，决定扩展、整改、合并或退出；
- 每季度复测基线，清理过期指标和承诺。

## 8. 建设路径与推广方法

| 阶段 | 关键动作 | 退出标准 |
| --- | --- | --- |
| 基线诊断 | 选定真实痛点，记录周期、返工、质量和成本 | 问题可量化，责任人明确 |
| 单点打透 | 选择高频、可验证、风险可控场景 | 产物能被第三方复核 |
| 可信固化 | 补 Schema、闸门、证据、权限和恢复 | 异常与攻击样本拦截回归通过 |
| 流程嵌入 | 接入迭代、角色分工和发布准入 | 团队独立使用，绕行可追踪 |
| 契约联动 | 复用编号、通道、知识和上游资产 | 无重复搬运，跨工具口径一致 |
| 规模运营 | 培训、度量、成本、版本和知识运营 | 收益跨周期复现，成本在预算内 |

核心经验：

1. 先治可信，再追求 AI 产能。
2. 先单点打透，再连接为体系。
3. 知识与工具同建，运营与建设同时开始。
4. 推广靠流程默认路径和可信证据，不靠一次培训或行政动员。
5. 工具组合需要有退出机制，避免只增不减、维护成本失控。

## 9. 适用边界与演进方向

### 9.1 适用边界

- 机械流程可无人值守，但业务语义、重大缺陷和发布取舍需要人工复核。
- E2E 不替代真机矩阵、性能压测和安全渗透。
- 局部影响分析用于迭代反馈，发布仍需全量兜底。
- 机器全绿只表示满足已定义检查，不代表业务风险为零。
- 哈希链主要防陈旧组合和事后篡改，不独立防高权限恶意内部人。

### 9.2 状态管理

**已落地或由材料验证**：全流程工具组合、受控 RAG、契约化、证据链、只读通道、双知识库和缺陷回流。

**持续校准**：启发式规则、历史基线、版本兼容、同环境性能、定位健康、断言强度与知识长期收益。

**规划中**：协作平台与 IM 自动受理、更多角色评审、BI 受控自动化建设、组织级看板和项目初始化增强。规划项不得写成既有成果。

## 10. 非 E2E 工具的核心契约与实例

> 本节的 JSON、YAML 和 Python 片段均为**独立、脱敏、机制等价**示例，使用虚构项目号、通用表名和示意路径，不对应任何真实工程，也不能直接还原私有实现。

### 10.1 确定性与语义的分工点

| 工具 | 确定性环节（机器） | 语义环节（AI） |
| --- | --- | --- |
| `prd-toolkit` | 结构锚点、双源核验、编号与引用检查 | 业务规则、交互语义与正文 |
| `rv-toolkit` | 结论枚举、引用溯源、版本快照、闭环统计 | 问题发现与专业判断 |
| `spec-toolkit` + `xx-spec-writing` | 骨架、审计快照、M/L 检查、契约对拍 | YAML 契约与章节语义 |
| `xx-spec-coding` | 范围解析、编译与代码闸、修复上限 | 编码实现与方案选择 |
| `unit-test-selfcheck` | 真实执行、执行原文存档、十项归档闸 | 业务语言与缺陷分析 |
| `tc-toolkit` | 17 字段、RFC4180、编号与统计一致性 | 用例与预期语义设计 |
| `db-query-assistant` | 只读通道、模板、截断、审计与基线对比 | 查询意图与结果解读 |
| `defect-hunter` | 症状路由、规则扫描、日志检索 | 根因研判与修复建议 |
| `depr-check-toolkit` | 模板执行、断言、环境分工与归档 | 异常解读与处置建议 |

### 10.2 设计评审：结论必须绑定版本并逐条溯源

```json
{
  "document_ref": "PRD-PUB-01",
  "document_hash": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "review_round": 2,
  "conclusion": "pass_with_revision",
  "findings": [
    {
      "id": "F-1",
      "severity": "high",
      "quote": "该状态下允许重复提交。",
      "source": { "chapter": "3.2", "paragraph": 2 },
      "decision": "must_fix",
      "fixed": true
    }
  ],
  "closure": { "total": 1, "resolved": 1 }
}
```

结论枚举固定为 `pass / pass_with_revision / fail`，不允许中间态。每条问题必须引用可定位的原文位置；被评审文档摘要变化即触发复审信号。存在未处置的严重问题时，评审结论不能为 `pass`。

### 10.3 规格编码：先解析范围，再人工确认，最后写码

范围表达式把自然语言指令转换为可追踪的文档区间：

| 记号 | 定位目标 |
| --- | --- |
| `T-08` / `T-08..T-13` | 计划任务（单点或区间） |
| `API-TR-12` / `API-TR-04..API-TR-09` | 后端接口（单点或区间） |
| `F-05` / `F-01..F-14` | 前端页面（单点或区间） |
| `be` / `fe` / `all` | 整端展开 |

```json
{
  "scope": "T-07,T-08,API-TR-13..API-TR-14",
  "resolved": [
    { "mark": "T-07", "doc": "plan", "chapter": 2, "lines": [101, 140] },
    { "mark": "T-08", "doc": "plan", "chapter": 2, "lines": [141, 178] },
    { "mark": "API-TR-13", "doc": "backend", "chapter": 3, "lines": [210, 255] },
    { "mark": "API-TR-14", "doc": "backend", "chapter": 3, "lines": [256, 301] }
  ],
  "required_inputs": ["instruction_set", "forbidden_rules", "error_code_table"],
  "status": "confirmed_by_human"
}
```

解析失败即退出，禁止猜测章节；`status` 未确认前不得写任何代码。范围外的存量文件原则上不动，例外必须列入人工确认清单。

### 10.4 用例生产：写入门前校验 17 字段与编号一致性

用例行固定 17 列，步骤与预期必须逐条编号且条数一致。机器负责 CSV 引号、换行、RFC4180 序列化、重复拒绝和统计回写。

```python
import re

EXPECTED_COLUMNS = 17

CASE = [
    "模块", "-", "订单提交必填校验", "维护人", "功能测试",
    "P1", "手动", "-", "-", "-", "订单处于可提交状态",
    "1. 清空必填字段后点击提交\n2. 查看页面提示",
    "1. 提交被拦截\n2. 出现必填提示",
    "-", "", "V1.0", "-",
]


def numbered(text: str) -> list:
    return re.findall(r"(?m)^\d+\.", text or "")


assert len(CASE) == EXPECTED_COLUMNS
assert len(numbered(CASE[11])) == len(numbered(CASE[12])) == 2
```

同一机制还负责：表头与枚举合法、必填字段存在、留空字段使用占位符、禁用词与警告词拦截、统计段可由 CSV 实际值回写。这样“步骤与预期不一致”在写入时就被拒绝，而不是等到评审才发现。

### 10.5 数据通道：模板即受控查询

```yaml
templates:
  pending_documents:
    description: 按时间窗查询未完成单据
    env: test
    sql: |
      SELECT doc_no, status, created_at
      FROM business_document
      WHERE status = 'pending'
        AND created_at >= :window_start
      ORDER BY created_at DESC
      LIMIT 20
    params:
      window_start: "{run_start}"
    max_rows: 100
    read_only: true
    audit: true
```

模板由真实执行验证后入库；参数化执行；结果行数上限截断；查询内容全量审计。模板可以在批次基线对比中过滤已登记明细，让连续核验报告只呈现新增项。

### 10.6 缺陷定位：证据不足就标记未知，而不是补一段解释

```json
{
  "bug_id": "BUG-DEMO-0001",
  "symptom": "页面提示保存成功，但单据状态未变化",
  "code_refs": [
    { "path": "<service>/order/OrderSubmit.java", "line": 214, "note": "状态更新分支" }
  ],
  "log_refs": [
    { "file": "app.log", "line": 882, "event": "save:ok" }
  ],
  "db_evidence": {
    "query": "SELECT doc_no, status FROM business_document WHERE doc_no = :doc_no AND created_at >= :run_start",
    "status": "confirmed",
    "matched": 0
  },
  "root_cause_class": "biz",
  "confidence": "medium",
  "status": "pending_review"
}
```

根因枚举固定为 `env / case-infra / case-data / case-deps / biz`。任何证据缺失时只能降低置信度或输出取证计划；`biz` 结论必须人工复核，确认后绑定至少一条回归用例。

### 10.7 专项核验：断言与跳过分开记账

```yaml
templates:
  - id: "SIM-EXAMPLE-01"
    group: "simulate"
    envs: ["test"]
    skip_envs: ["prod"]
    sql: |
      SELECT plan_row_id, expected_amount, actual_amount,
             (expected_amount - actual_amount) AS amount_diff
      FROM depr_plan_example
      WHERE business_period = :period
    assert: "col_zero"
    assert_columns: ["amount_diff"]
```

| 断言类型 | 含义 |
| --- | --- |
| `rows_zero` | 结果应为 0 行，允许有据可查的白名单豁免 |
| `rows_positive` | 结果应至少 1 行，用于口径异常提示 |
| `agg_zero` | 聚合行或全部数值列必须为 0 |
| `col_zero` | 指定列在所有结果行中必须为 0 或空 |
| `SKIP` | 模板按环境规则预期跳过，与执行失败分开记账 |
| 无断言 | 仅执行展示，人工解读 |

断言不硬编码业务金额，只使用等式、覆盖和衔接关系。版本化模板显式声明环境，避免把一套公式或阈值机械套用到所有环境。

### 10.8 单测自检：执行原文是报告的硬证据

报告中的每个结论必须对应真实执行记录：测试执行原文存档、验证 SQL 先执行后落笔、汇总表与明细一致、缺陷编号一次生成不改号。归档前经过十项闸门，任一失败禁止交付。这保证“写了单测”不等于“跑了单测”，“跑了单测”也不等于“结论与原文一致”。
